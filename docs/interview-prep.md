## 1. 中文简历项目描述

### 1.1 一句话版（简历项目名下方的副标题）

> 面向电商客服场景的可追溯 RAG 系统：结构化事实走 PostgreSQL、政策回答强制引用、
> 退款与转人工由确定性规则决定，并用 136 条业务用例 + 58 条检索金标把效果做成可复算的。

### 1.2 标准版（约 320 字，适合简历"项目经历"正文）

**ShopMate 电商智能客服与轻导购助手**（个人项目，全栈）

**背景**：通用聊天机器人容易编造价格、库存和退款政策，而退款、赔付这类高风险决策又不能交给模型。
项目目标是把"能查的事实"和"能给的建议"分开：事实只来自数据库，政策必须带引用，资金类结论由规则和人工决定。

**职责**：独立完成从 PRD、架构、数据/工具/API 契约，到 FastAPI 后端、Vue 3 前端、
Docker 编排与生产部署、评测与压测的全链路；共 113 个 Python 文件（约 2.3 万行）、31 个 Vue 组件。

**技术方案**：模块化单体 + 单 Agent + 确定性工具层。三条路径分流——商品/订单/物流走 PostgreSQL
结构化工具；政策/FAQ 走本地 BGE-M3（一次前向产出 dense 1024 + sparse 稀疏权重）→ Milvus
`hybrid_search` 各取 top30 → RRF(k=60) 融合 → PostgreSQL 二次复核租户/地区/版本/生效期 → 4–8 片段 + 稳定引用 ID；
退货资格与转人工走代码规则。写操作全部带 `idempotency_key`，订单/工单从认证上下文校验归属。
前端 SSE 用七类固定事件（meta/tool_status/product_card/citation/delta/done/error），后端决定事件结构，不由模型决定。

**难点**：① 评测指标一度复现不出来——根因是数据初始化脚本**无条件重写**评测集，
把手工补的 36 条用例静默覆盖，改为"存在即不覆盖"后指标才稳定；② 政策回答出现过
`NO_EVIDENCE [c1]…` 被当答案返回的 fail-open（哨兵用精确相等判定），定位后改成「剥离引用标签/空白/句末标点再比对」，并用 5 类输入补了回归测试（阶段 16 已修，历史评测数字未重跑）；
③ 压测与延迟口径最初把不同轮次混在一起统计，改为逐条打 `latency_kind` 分桶后才可信。

**结果（均为本机实测，可复算）**：58 条检索金标（50 条有金标文档）上 Recall@1/3/5/10 = 1.00、MRR@10 = 1.00、
主引用正确率 1.00；136 条业务/安全用例上任务成功率 0.6324、越权拦截 8/8、转人工精确率 1.00、
注入用例 11/11 未泄漏；聊天轮 P50/P95 = 25.63/43.10 ms，SSE 首 token 24.99/42.39 ms；
20→40 并发吞吐 23.08→29.61 req/s（+28.3%，已饱和）；门禁 600 项后端测试通过、86 项安全测试、
124 项前端组件测试、16 条 E2E、部署安全复查 34 项全过。
**同时明确短板**：政策问答严格拒答率 0/7、政策类问题仅 16/36 进入 RAG、混合检索在该语料上测不出优于 dense-only。

### 1.3 简历条目版（直接贴到项目栏，控制在 6 条）

- 设计并实现模块化单体 RAG 客服系统：FastAPI + PostgreSQL + Redis + Milvus + 本地 BGE-M3 + Vue 3，
  三条路径（结构化工具 / 知识检索 / 确定性规则）职责分离。
- 实现 BGE-M3 单次前向双向量（dense 1024 L2 归一化 + sparse lexical weights），
  Milvus `hybrid_search` 双路 top30 + RRF(k=60)，再用 PostgreSQL 复核店铺/地区/版本/生效期，
  引用可追到文档+章节+版本+生效日期；任一路失败显式报错，不静默降级。
- 实现 10 类意图路由、查询改写、FAQ 缓存、输入/输出护栏与 PII 脱敏；
  11 条提示注入用例全部未泄漏系统提示词或密钥。
- 实现订单/物流/退货资格/退货申请/转人工 5 个工具，写操作幂等 + 后端归属校验；
  8 条跨用户越权用例全部拦截，转人工精确率 1.00。
- 建立可审计的评测体系：136 条业务/安全用例 + 58 条检索金标 + Locust 压测，
  并写了一个**不 import 评测脚本**的独立复算脚本，逐项对账报告数字（当前 0 不一致项）。
- 完成生产化：只读根文件系统、非 root、`cap_drop: ALL`、资源与日志限制、一次性迁移服务，
  并用静态安全复查脚本（34 项）作为发布门禁。

## 2. 面试问答提纲（15 题）

> 每题结构：**考点** → **30 秒作答** → **证据** → **别说**。
> 原则：有数字就给数字并带上口径，没有数字就说定性；缺陷主动说，比被追问出来好。

### Q1. 用一句话介绍这个项目，你自己写了哪些部分？

- **考点**：表达清晰度 + 边界诚实。
- **作答**：一句话定位（可追溯的电商客服）+ 我负责的边界：PRD、契约、后端、前端、编排、评测全部在本仓库自己实现；
  架构思路参考过公开项目与课程资料，但代码和数据没有复制。
- **证据**：`docs/01-github-research.md`（参考仓库 URL + license）、`docs/project-status.md` 各阶段记录。
- **别说**："参考某开源项目实现了……"——会被追问"哪部分是原创"。

### Q2. 为什么不让 LLM 直接回答价格、库存、退款？

- **考点**：是否理解 LLM 的能力边界与业务风险。
- **作答**：三类风险——事实易漂移（价格/库存有时效）、资金动作不可逆、责任不可追溯。
  所以定了铁律：结构化事实只来自 PostgreSQL/受控缓存；金额与退款由确定性规则判定，LLM 只解释规则结果；
  查不到就回"当前无法确认"并给下一步。工具返回统一信封带 `as_of` 与 `trace_id`，答案里的数字必须能在载荷里找到。
- **证据**：`AGENTS.md` §4；`tools/schemas.py` 的信封；结构化 faithfulness 0.8318（107 轮，数字可溯源比例）。
- **别说**："用 prompt 约束模型不要编"——prompt 不是结构性保障。

### Q3. 混合检索具体怎么做的？为什么最后说"测不出收益"还保留？

- **考点**：RAG 细节 + 是否敢报负面结论。
- **作答**：BGE-M3 同一次前向出 dense(1024, 写入和查询都 L2 归一化) 与 sparse lexical weights；
  Milvus 一次 `hybrid_search`，两路各 top30，RRF k=60 融合；融合结果再回 PostgreSQL 复核
  shop/kb/locale/region/文档状态/生效期，最后在 token 预算内选 4–8 片段并生成稳定引用。
  消融：关掉 sparse 只走 dense，在 58 条金标（50 条有金标）上 Recall、MRR、context precision、行为正确率全部相同——
  因为这个语料只有 27 条有效向量（Milvus `count(*)` 28，含 1 条孤儿），问题与政策原文高度重合，dense 已经把金标排到第 1。
  保留 sparse 的理由是精确词（型号/金额/编号）鲁棒性和契约要求，不是"提升召回"。
- **证据**：`rag/retrieval.py`、`rag/milvus_store.py`（`RRFRanker(k=rrf_k)`）、报告 2.4.3。
- **别说**："混合检索提升了召回率 xx%"。

### Q4. 引用是怎么保证不编造的？

- **考点**：护栏是否成体系，而不是一句 prompt。
- **作答**：四层——① 检索层给每个片段生成稳定 `[cN]`；② 生成 prompt 要求每个结论带标签、不足则输出 `NO_EVIDENCE`；
  ③ 输出护栏做三件事：引用标签必须来自本次提供的集合、承诺类措辞（保证退款/赔偿）拦截、
  未标注结论转人工；④ 无证据（top-1 相似度 < 0.62）直接拒答并给人工入口。
  我也主动说缺陷：哨兵判定用的是精确相等，模型输出 `NO_EVIDENCE [c1]` 时会绕过，实测 2 条（eval-058/061），
  修法是去标签去空白后比较 + 补回归用例，但这属于业务逻辑变更，我留着等授权。
- **证据**：`rag/policy_qa.py`（L397 精确相等、`citation_issues`、`commitment_issues`）、报告 2.9.0；
  引用合规率 1.00（5/5 answered）。
- **别说**："有引用就不会编"——引用对但结论越界一样是错。

### Q5. 意图路由准确率只有 0.7059，为什么不用小模型或 LLM 分类？

- **考点**：技术选型取舍 + 对指标的分母是否清楚。
- **作答**：当前是关键词加权规则，好处是零延迟（聊天轮 P50 25.63 ms）、可解释、可单测（56 个用例）；
  代价是长尾表述漏判，36 条政策类问题只有 16 条进了 RAG。当时没用小模型，是因为要先有一个稳定基线，
  而且路由错了要能一眼看出为什么错。要改的话我会先加"知识型兜底"（政策词未命中但形如疑问句 → 走 RAG 拒答路径），
  再评估是否换成小分类模型，并且要保留规则回退。
- **证据**：`agents/router.py`（10 类 `Intent`）、`tests/unit/test_intent_router.py`、报告 2.6/2.9.1。
- **别说**："0.7 已经不错"——要给出分母和失败类型。

### Q6. 幂等是怎么实现的？重复提交会怎样？

- **考点**：写操作的工程严谨性。
- **作答**：写工具（退货申请、转人工）必须带 `idempotency_key`，落一张幂等表，键唯一；
  同一用户+同一操作+同一 key 第二次进来直接返回第一次的结果，不产生第二条记录；
  审计表 `tool_calls` 记录操作者、会话、输入摘要、结果、`latency_ms`，不记完整 PII。
  另外退货资格判定把 `submitted/under_review/approved/completed` 都视为阻断状态，防止"已退货还能再退"。
- **证据**：`db/repositories/idempotency.py`、`db/repositories/orders.py::find_active_return`、
  `tests/integration/test_order_return_handoff_db.py`、报告 §20.6 A 项（含 1 处业务规则变更的说明）。
- **别说**："前端按钮置灰"——那不是幂等。

### Q7. 越权是怎么防的？为什么只报 8 条？

- **考点**：是否真的在后端做校验，是否理解样本量。
- **作答**：订单/物流/退货/工单的 `user_id`、`shop_id` 都从认证上下文取，路由层和 repository 层各校验一次；
  不信任前端传的 user_id。检索侧也做租户过滤：Milvus 只做初筛，最终以 PostgreSQL 元数据复核为准。
  8 条是数据集里带 `authorization` 标签的用例数（eval-095/101/102/103/104/105/106/109），
  分母写进原始结果 `authorization_cases=8`，避免"分母变了指标消失"；样本确实小，
  跨店铺 admin 的运行时用例还没构造。
- **证据**：`verify_stage13.py` 输出 `authorization=8 / unauthorized_blocked=8`；`tests/security/test_order_permissions.py`。
- **别说**："越权拦截 100%"不带分母。

### Q8. 你怎么证明这些指标不是你编的？

- **考点**：可复现性意识——这题是分水岭。
- **作答**：三层。① 数据集指纹：136 条 / sha `7606cfce…`，58 条 / sha `856f3338…`，
  磁盘、原始结果里的 `datasets` 字段、报告三处必须一致；② 原始结果逐用例落盘（含 `latency_kind`、`first_delta_ms`、`index` 快照）；
  ③ 我另写了一个 `verify_stage13.py`，**故意不 import 评测脚本**，只读 records 重算所有头条指标，不一致就退出码 1。
  另外踩过的坑也写进报告：初始化脚本会覆盖评测集，导致"报告 136、磁盘 100"反复出现。
- **证据**：`scripts/verify_stage13.py`；本轮运行输出"全部一致（独立复算 == 原始结果）"。
- **别说**："我跑过，结果是……"——没有可复算路径就等于没有证据。

### Q9. 压测结论是什么？瓶颈在哪？

- **考点**：性能分析的归因能力。
- **作答**：本机单 worker + CPU 推理，20 并发 60 秒 1350 请求 0 失败、P95 570 ms；
  40 并发 1762 请求 2 失败（0.11%，`RemoteDisconnected`）、P95 2400 ms、P99 3200 ms；
  吞吐 23.08 → 29.61 req/s（+28.3%），但 P95 翻了 4.2 倍，说明**已经饱和**。
  瓶颈不是数据库，是进程内 BGE-M3 CPU 推理串行化：所有政策问答共享一个模型实例，
  连不碰 embedding 的商品/订单接口也被同一事件循环拖慢。所以单 worker 部署我不能承诺 40 并发下的 P95。
- **证据**：两个 CSV 的 `Aggregated` 行（`23.0833` / `29.6058`）、报告 2.8。
- **别说**："支撑 40 并发"——那是把饱和点当容量。

### Q10. 政策问答 29 条可答只答出 5 条，这系统还有用吗？

- **考点**：面对难看数字的态度。
- **作答**：先把 36 条的 status 分布说清楚：**answered 5 / handoff 4 / refused 27**（5 + 4 + 27 = 36）。
  27 条 refused 拆成两块——**7 条是证据门槛正确拦截**（top-1 相似度低于 0.62，且主题在语料里确实没有），
  **20 条是 7B 模型自己判"依据不足"**（证据已检索到，模型仍拒答，属模型过度保守），**7 + 20 = 27**。
  另有 **4 条**是模型写了结论但没带 `[cN]` 引用，被输出护栏转成人工（`handoff`，`uncited_claim`），
  **这 4 条不属于 refused**，不能并进 27 里数。
  也就是说**确定性护栏是对的，短板是那个 7B 模型**。换更强模型或换 prompt 策略可以改善，
  但我不会把这个 0.17 包装成"检索不行"或"系统可用"。同一批数据上无答案用例正确拒答 7/7，
  说明"不该答的时候不答"这条是通的。
- **证据**：报告 2.5.2 的拒答来源拆解表；原始结果 `parts.policy_llm.status_counts`
  = `{answered: 5, handoff: 4, refused: 27}`，逐条 `reasons` 计数为 `no_evidence` 7 / `model_no_evidence` 20 /
  `uncited_claim` 4（后者 status 全是 `handoff`）。
- **别说**："模型能力问题跟我无关"——路由、prompt、门槛都是我设计的。

### Q11. 你说"登录后被弹回登录页"，怎么定位的？

- **考点**：前端状态管理 + 调试方法。
- **作答**：现象是登录接口 200 但路由守卫立刻跳回 `/login`。先看守卫条件，依赖 `isAuthenticated` computed；
  再看 token 存放处，是模块级 `let accessToken`，不是响应式数据，computed 首次求值 false 后永远缓存 false。
  改成 `shallowRef` 后恢复，并补了一条"先求值 → 登录 → clearSession"的回归用例防止再犯。
  顺带发现两个连带问题：登录失败没提示（catch 里先赋 error 再刷新验证码，后者清空了 error）、
  刷新必掉登录（后端 cookie `Path=/api/v1/auth`，页面读不到 CSRF cookie），后者在代理层重写 path 兜底。
- **证据**：`frontend/src/api/client.ts`、`frontend/src/views/LoginView.vue`、`vite.config.ts`、`web/nginx.conf`、`docs/project-status.md` §19。
- **别说**："改了个 bug"——要说清链条：非响应式 → computed 缓存 → 守卫误判。

### Q12. 生产部署做了哪些加固？踩过什么坑？

- **考点**：是否真的部署过，而不是只写 Dockerfile。
- **作答**：独立项目名与独立卷、只有 web 暴露 8080、api/web 只读根文件系统 + tmpfs + `cap_drop: ALL` +
  `no-new-privileges` + CPU/内存上限、日志轮转 10MB×3、迁移拆成一次性 `migrate` 服务、镜像必须显式 tag。
  坑有三个：① `pids_limit` 与 Compose v5 的 deploy limits 冲突，只能二选一；
  ② nginx `server_tokens` 必须放 http 块，否则容器起来就退出；
  ③ `TRUSTED_HOSTS` 只填真实域名时，容器 healthcheck 打 `127.0.0.1` 会被判 400 → api 永久 unhealthy，
  所以模板里必须带上回环地址，并补了回归用例。
- **证据**：`compose.prod.yaml`、`web/nginx.prod.conf`、`tests/unit/test_trusted_hosts.py`（9 条）、
  `docs/project-status.md` §22.7；`check_deploy_security.py` 34 PASS。
- **别说**："用了 Docker 就算部署完成"。

### Q13. 如果给你两周，你先修什么？

- **考点**：优先级判断，是否基于数据。
- **作答**：按报告 2.10 的优先级。P0 的 `NO_EVIDENCE` fail-open **已在阶段 16 修复**

## 4. 使用建议

- 简历里**最多放 2–3 个数字**（推荐：R@1 1.00 + 136/58 双数据集 + 600 项测试），
  其余留到面试展开——数字堆太多会被追问到答不上来。
- 被问"效果怎么样"时，先给主结论，再主动给一个负面结论（混合检索测不出收益 / 政策问答 5/29），
  可信度比只报喜高得多。
- 任何一次面试前跑一遍 `uv run python scripts/verify_stage13.py`，确保你引用的数字仍然成立。
