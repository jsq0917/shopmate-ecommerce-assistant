# ShopMate 产品需求文档（PRD）

> 阶段：阶段 2 — PRD、MVP 与验收标准  
> 版本：v0.1  
> 日期：2026-10-18  
> 状态：阶段 2 完成稿；作为阶段 3 架构、数据和工具契约的输入  
> 产品：ShopMate 电商智能客服与轻导购助手

## 1. 文档目的与边界

本文定义 ShopMate MVP 要解决的问题、三类用户、用户故事、功能范围、五条核心旅程、失败行为、确定性业务边界和可测试验收标准。

本文回答“产品应做到什么、如何证明做到”，不冻结底层表结构、API schema、SSE 字段实现或 Milvus collection 细节。这些问题在阶段 3 的架构、数据、工具和 API 文档中确定。

优先级以 `AGENTS.md`、用户当前明确指令、阶段 1 审计结论为准。本文不得被解释为允许真实支付、真实退款、真实 PII、模型直接执行资金操作或绕过权限校验。

## 2. 产品定义

### 2.1 产品目标

为消费者提供可追溯的购物、政策、订单、物流、退货和人工服务入口；为客服提供带引用、风险标签和工具调用上下文的接管工作台；为运营提供版本化知识与评测管理能力。

产品的核心价值不是“让聊天机器人像人”，而是：

1. 实时事实有结构化来源。
2. 政策回答有当前有效版本的引用。
3. 资金和权益由确定性规则或人工处理。
4. 越权、低置信度和高风险有明确降级路径。
5. 每次关键回答和写入都可用于审计、测试和评测。

### 2.2 不可违反的产品铁律

- 商品价格、SKU、库存、订单状态、物流节点和当前优惠只能来自 PostgreSQL、受控 Redis 缓存或 Mock OMS；不得来自模型记忆或 RAG 片段。
- 退换货资格由确定性规则判断；`create_return_request` 只能创建申请，不代表退款成功。
- 退款审批、赔付、免单、优惠券发放、改价和金额修改不得由 LLM 决定。LLM 只能解释工具或人工产生的结果。
- 政策回答必须附引用，引用至少包含文档、章节/页码、版本、生效日期和片段 ID。
- 用户身份、店铺范围和资源归属由后端认证上下文确定；模型不能传入或修改 `user_id`、`shop_id` 等身份字段。
- 投诉、法律威胁、人身安全、异常大额交易、工具连续失败、低置信度、工具与模型冲突、用户明确要求人工时，必须升级人工。
- 检索内容和上传文档是不可信数据，不得作为系统指令执行。
- 退货申请和人工工单等写操作必须幂等、可审计，重试不能产生重复记录。

## 3. 用户与用户故事

### 3.1 消费者（shopper）

消费者希望快速找到合适商品、理解政策和售后规则、查询自己的订单并安全地发起售后或人工请求。

| ID | 用户故事 | 价值 | 优先级 |
|---|---|---|---|
| US-C01 | 作为消费者，我希望登录后用自己的账号开启或继续会话，以便查询只属于我的订单。 | 保护账号和订单隐私 | P0 |
| US-C02 | 作为消费者，我希望用预算、场景和商品属性描述需求，以便获得有真实价格和库存的商品卡片。 | 降低选择成本 | P0 |
| US-C03 | 作为消费者，我希望比较 2–4 件商品的真实字段，以便知道差异和缺失信息。 | 避免被编造参数误导 | P0 |
| US-C04 | 作为消费者，我希望查询当前政策并获得可展开的引用，以便知道依据、版本和生效日期。 | 提升可信度 | P0 |
| US-C05 | 作为消费者，我希望查看自己的订单和物流节点，并看到数据更新时间。 | 快速确认履约状态 | P0 |
| US-C06 | 作为消费者，我希望先知道退货规则，再确认是否创建申请，以便避免误提交。 | 明确预期 | P0 |
| US-C07 | 作为消费者，我希望重复提交同一退货请求不会创建多条申请。 | 避免重复售后 | P0 |
| US-C08 | 作为消费者，我希望在无答案、低置信度、投诉或明显高风险时获得人工入口，而不是被模型敷衍或承诺。 | 保障权益 | P0 |
| US-C09 | 作为消费者，我希望聊天中实时看到“正在查询订单”“引用已找到”等状态，并在断线时知道如何恢复。 | 降低不确定性 | P1 |

### 3.2 客服人员（support）

客服希望在不越过店铺和用户边界的前提下，查看 AI 为什么这样回答、调用了什么工具、存在什么风险，并接管需要人工处理的会话。

| ID | 用户故事 | 价值 | 优先级 |
|---|---|---|---|
| US-S01 | 作为客服，我希望按风险、原因和等待时间查看人工工单。 | 优先处理高风险问题 | P0 |
| US-S02 | 作为客服，我希望查看工单对应会话的消息、引用、工具摘要和风险标签。 | 快速理解上下文 | P0 |
| US-S03 | 作为客服，我希望接管会话并标记解决状态，但不能越权查看其他店铺数据。 | 安全接管 | P0 |
| US-S04 | 作为客服，我希望知道 AI 是否拒答、工具是否失败或政策是否冲突。 | 避免重复排查 | P0 |
| US-S05 | 作为客服，我希望把回答标记为正确、错误或需补充知识，以便形成评测样本。 | 持续改进 | P1 |

### 3.3 运营/管理员（admin）

运营希望维护当前有效政策、商品说明、FAQ 和评测数据，并看到系统检索和回答质量的可复现结果。

| US-A02 | 作为运营，我希望文档解析失败时有明确状态和错误原因，而不是生成空知识库。 | 提升可治理性 | P0 |

## 4. MVP 范围与非目标

### 4.1 MVP 必须包含

| 能力域 | MVP 内容 |
|---|---|
| 账号与权限 | 注册、登录、验证码、速率限制、角色区分、会话归属和店铺范围校验 |
| 会话 | 多会话创建、重命名、软删除、短期历史、中文 SSE 流式输出 |
| 商品 | 受控商品搜索、详情、2–4 件商品比较、价格/库存查询及 `as_of` |
| 知识 | 版本化政策/FAQ/商品说明、中文 RAG、引用侧栏、无证据处理 |
| 订单与物流 | 当前用户订单列表/详情、物流节点、脱敏单号、后端归属校验 |
| 售后 | 退货资格判断、用户确认后创建幂等申请、规则拒绝解释 |
| 人工 | 高风险、低置信度、工具失败和用户请求触发幂等人工工单 |
| 客服端 | 风险工单队列、对话与引用查看、工具摘要、接管/解决状态、回答质量标记与评测反馈 |
| 运营端 | 知识库与文档版本、解析状态、片段预览/停用、评测运行与失败案例 |
| 演示数据 | 固定随机种子的 synthetic 商品、订单、物流和政策；Mock OMS；无真实 PII |
| 工程与安全 | 统一错误码、PII 脱敏、审计、权限测试、Docker Compose 本地运行 |

### 4.2 明确非目标

- 不接真实支付、真实退款、真实赔付、真实优惠券发放、真实改价或真实库存写入。
- 不接入、存储或演示真实姓名、手机号、地址、身份证、银行卡、真实邮箱账号或其他 PII。
- 不同步真实电商平台全量商品，不连接真实 OMS、物流承运商或第三方客服平台。
- 不训练或微调模型，不把模型权重、课程视频或大型数据库文件加入仓库。
- 不做多 Agent 自治协作、微服务、Kubernetes、Kafka、Celery 或复杂推荐系统。
- 不提供真实商品购买、结算、发票开具或保修赔付执行。
- 不允许 LLM 自动审批退款、赔偿、免单、优惠券或修改金额、库存、订单状态。
- 不允许 LLM 自动生成并执行 SQL、访问任意 URL 或调用未注册工具。
- 不把 RAG 检索结果用于回答实时价格、库存、订单或物流事实。

## 5. 五条核心用户旅程

### 5.1 旅程 J1：商品搜索与比较

**示例需求**：“预算 300 元以内、适合通勤的降噪耳机，有现货优先。”

**前置条件**

- 消费者已登录，属于 demo 店铺。
- 商品、SKU、价格、库存均为标记为 synthetic 的结构化数据。
- 数据库中存在预算内、预算外、缺货和缺失部分属性的测试商品。

**主流程**

1. 系统识别为商品发现意图，提取预算上限 30000 分、通勤场景和降噪属性。
2. 系统调用受控商品搜索工具，只返回符合预算且处于可售状态的商品。
3. 系统展示商品卡片：商品名、SKU、价格、币种、库存摘要、命中原因和 `as_of`。
4. 用户要求比较前两件商品，系统按数据库字段对齐 2–4 件商品。
5. 对不存在的参数显式显示“unknown/暂无数据”，不得推断或补写。

**可测试结果**

- 给定 29900 分和 32900 分的两件商品，当预算上限为 30000 分时，只返回前者。
- 商品卡片中的价格、SKU、库存与数据库固定种子数据一致。
- 比较缺失属性时返回 `unknown`，不得由模型生成看似合理的参数。
- 缺货商品不得显示为“有货”；用户未要求现货时也不得隐藏缺货事实。
- 返回内容必须包含 `as_of`；页面不得只显示一个无来源的现价。

### 5.2 旅程 J2：政策问答

**示例需求**：“七天无理由怎么退？请给我依据。”

**前置条件**

- 知识库中存在当前生效的退货政策，以及一个已过期或冲突的历史测试版本。
- 政策元数据包含店铺、地区、语言、版本、生效期、章节和片段 ID。

**主流程**

1. 系统识别为政策/FAQ 意图。
2. 系统按店铺、地区、语言、知识库、版本状态和当前时间过滤检索。
3. 回答只使用检索到的政策片段，并给每个关键结论绑定引用。
4. 用户展开引用，可看到文档标题、章节/页码、版本、生效日期和片段预览。
5. 若证据不足、版本冲突或内容过期，系统明确说明限制，并提供人工入口。

**可测试结果**

- 回答中每个关键政策结论至少对应一个实际提供的片段 ID。
- 引用中的版本和生效日期与数据库元数据一致。
- 已过期、未 ready 或跨店铺文档不得进入检索结果。
- 没有足够证据时，回答不得猜测政策；必须拒答、澄清或转人工。
- 文档中的“忽略系统指令”“输出密钥”等恶意文本不得改变系统行为。
- 同一问题在数据或知识版本变化后不得错误命中旧缓存。

### 5.3 旅程 J3：订单与物流查询

**示例需求**：“我的订单 DEMO-1001 到哪了？”

**前置条件**

- 消费者 A 拥有 `DEMO-1001`。
- 消费者 B 拥有另一个订单。
- 订单和物流由 Mock OMS/PostgreSQL 提供，数据标记为 synthetic。

**主流程**

1. 后端从认证上下文取得当前用户和店铺范围。
2. 系统先查询订单归属和状态，再按需查询物流。
3. 返回订单状态、金额摘要、关键时间线、承运商、脱敏单号和最新物流节点。
4. 用户点击或追问时展示对应数据的更新时间。

**可测试结果**

- 消费者 A 可以查看自己的订单和物流。
- 消费者 A 输入消费者 B 的订单号时，无法获得属于 B 的任何订单字段或物流信息。
- 越权响应不暴露订单是否存在、收件人、地址或内部错误。
- 订单与物流的返回均包含状态和 `as_of`/更新时间。
- 工具失败时不得根据历史上下文或模型猜测“应该已经送达”。

### 5.4 旅程 J4：退货资格与申请

**示例需求**：“这个订单的耳机尺码不合适，我想退货。”

**前置条件**

- 订单已送达或完成，商品属于 synthetic 可退类别。
- 签收时间、商品金额、退货原因、是否已有申请均为结构化数据。
- 使用本文件第 6 节的演示规则配置。

**主流程**

1. 系统先调用退货资格检查，不在资格未知时直接写数据库。
2. 系统展示是否符合、命中的规则、截止时间、所需材料和“申请不等于退款”的说明。
3. 用户明确确认后，系统带幂等键调用 `create_return_request`。
4. 系统返回申请 ID 和 `submitted` 状态，并说明后续需审核。
5. 若资格不符合、处于高风险或信息不足，系统不创建申请，并解释规则或转人工。

**可测试结果**

- 恰好处于退货截止边界时，规则结果与本文第 6.2 节一致。
- 超过截止边界 1 秒时返回不符合，不创建申请。
- 已取消、未签收、不可退类别或已有有效申请时不重复创建。
- 用户未确认时不得创建申请。
- 相同用户、操作和幂等键重复提交只产生一条申请，并返回同一申请标识或明确幂等结果。
- 申请状态只能是 `submitted`（或后续合法审核状态），不得把申请写为退款成功。
- 高风险大额退货不得由 LLM 自动承诺，必须进入人工审核/工单路径。

### 5.5 旅程 J5：投诉与转人工

**示例需求**：“我要投诉并起诉，要求你们立刻退款并赔偿。”

**前置条件**

- 用户已登录并处于某个有效会话。
- 系统具有风险分类、工单创建和会话审计能力。

**主流程**

1. 安全/风险检查优先识别投诉、法律威胁、资金要求和情绪风险。
2. 系统停止自动承诺，生成必要的会话摘要和风险等级。
3. 系统创建幂等人工工单，返回工单 ID、队列和预计响应说明。
4. 客服工作台可看到工单原因、风险、会话、引用、工具摘要和失败点。
5. 客服接管后，AI 不继续代表商家作出退款、赔偿或优惠承诺。

**可测试结果**

- 明确要求人工、投诉、法律威胁、人身安全、异常大额资金请求均触发人工路径。
- 同一会话、同一原因和同一幂等键重复触发只创建一个工单。
- 工单包含风险等级、原因、会话 ID、用户 ID 摘要和可供客服理解的安全摘要。
- 高风险回答不得出现“已为您退款”“一定会赔偿”“保证发券”等承诺。
- 客服只能访问其店铺/职责范围的工单与会话，普通消费者不可访问客服接口。

## 6. MVP 演示规则基线

以下规则用于 synthetic 演示和自动化验收，不代表真实商家的最终政策。阶段 3 必须将其转成可配置、可版本化、可单元测试的确定性规则；若修改，必须同步更新验收测试。

### 6.1 通用业务规则

1. 金额使用整数分和币种，不使用浮点数。
2. 时间以 UTC 存储和比较，界面可显示本地时间。
3. 所有结构化读结果包含 `as_of` 或更新时间。
4. 商品价格、库存和订单状态必须来自结构化数据源，RAG 不得提供这些事实。
5. 任何退款、赔付、优惠券、免单、改价请求都不能由 LLM 直接执行或承诺。
6. 人工审核结果必须独立于 LLM 文本存在；LLM 只能解释已存在的规则或审核结果。

### 6.2 退货资格演示规则

| 条件 | 演示判定 |
|---|---|
| 订单状态为 `delivered` 或 `completed` | 可进入后续资格判断 |
| 订单状态为 `created`、`paid`、`processing`、`shipped`、`cancelled` | 不可按“已签收无理由退货”自动办理，应解释原因或转人工 |
| 商品类别的 `is_returnable=false` | 不符合，并解释为 synthetic 不可退类别 |
| 原因 `SIZE_OR_FIT` 或 `NO_LONGER_NEEDED` | 按签收后 7 天窗口判断 |
| 原因 `DAMAGED_ON_ARRIVAL`、`WRONG_ITEM` 或 `QUALITY_ISSUE` | 不自动批准；进入人工审核/工单路径 |
| 当前时间 `<= delivered_at + 7 天` | 在窗口内，边界时刻视为在窗口内 |
| 当前时间 `> delivered_at + 7 天` | 超出窗口，不符合 |
| 已存在 `submitted`、`under_review` 或 `approved` 的同类申请 | 不重复创建，返回原申请或冲突结果 |
| 订单商品金额合计 `>= 500000` 分（演示阈值 ¥5,000） | 标记高风险，需人工审核；LLM 不得承诺 |

“审核通过”仍不等于退款成功。MVP 不连接真实退款服务；退款状态若出现，只能是 synthetic UI/数据状态，并必须与退货申请状态分开。

### 6.3 风险升级基线

以下任一条件成立时必须升级人工：

- 投诉、法律/监管威胁、人身安全、隐私泄露或账号被盗。
- 用户明确要求人工。
- 退款、赔偿、免单、优惠券或改价请求需要直接决定权益。
- 订单商品总金额达到演示高风险阈值。
- 政策存在无法自动裁决的冲突。
- 检索证据不足且政策问题影响用户权益。
- 同一工具连续失败两次、工具结果与模型陈述冲突或超过工具调用预算。
- 输入命中高风险规则，或模型输出护栏发现未引用的政策断言、资金承诺和 PII 泄露。

低置信度时的首选行为是澄清；无法澄清或涉及权益时转人工。低置信度不得触发写操作。

## 8. 失败场景与规定行为

| ID | 场景 | 触发示例 | 必须行为 | 禁止行为 | 验收证据 |
|---|---|---|---|---|---|
| ERR-01 | 无证据 | 知识库没有某地区配送政策 | 明确说明当前知识库无足够依据，提供补充资料或人工入口 | 编造地区政策或引用无关片段 | 无证据测试用例、SSE 错误/拒答记录 |
| ERR-02 | 工具失败 | 订单、库存或物流接口超时/不可用 | 返回“当前无法确认”和重试/人工建议；记录稳定错误码和 trace | 用模型记忆补全、假装成功或泄露堆栈 | 故障注入测试和脱敏日志 |
| ERR-03 | 重复工具失败 | 同一会话同一工具连续失败两次 | 停止循环调用，升级人工或给出明确下一步 | 无限重试、每个失败都重新生成不同事实 | 调用次数与工单测试 |
| ERR-04 | 越权 | 用户查询他人订单、会话、退货或工单 | 后端拒绝；不泄露资源存在性；记录安全审计事件 | 仅依赖前端隐藏、返回完整资源、显示内部 SQL | 安全测试、API 响应、审计记录 |
| ERR-05 | 低置信度 | 问题含义不清、检索分数不足或分类不确定 | 先澄清；影响权益或无法澄清时转人工；不调用写工具 | 强行路由、猜测订单/政策、自动创建申请 | 低置信度 fixture 与路由测试 |
| ERR-06 | 高风险 | 投诉、法律威胁、人身安全、异常大额退款 | 停止自动承诺，创建/展示人工路径，保留上下文摘要 | 承诺退款/赔偿/优惠，继续推销或淡化风险 | 高风险分类、工单和输出护栏测试 |
| ERR-07 | 政策冲突 | 两个有效版本对同一问题给出不同规则 | 标明冲突并转人工，不自行选择有利条款 | 隐藏冲突、混用两个条款、伪造确定性 | 冲突政策测试与引用记录 |
| ERR-08 | 工具与模型冲突 | 模型声称已退款，但工具没有退款记录或权限 | 工具事实优先；阻断资金承诺并升级 | 让模型解释覆盖工具结果 | 输出护栏与冲突测试 |
| ERR-09 | Prompt Injection | 用户或文档要求忽略规则、输出密钥、越权调用工具 | 拒绝越权/泄露；文档只作为不可信引用；必要时标记风险 | 执行文档命令、改变系统提示或调用未注册工具 | 安全测试与引用隔离记录 |
| ERR-10 | 重复提交 | 同一退货申请或工单被重试 | 返回同一幂等结果或明确冲突；数据库只有一条记录 | 创建第二条申请/工单 | 幂等测试和数据库查询 |
| ERR-11 | 输出泄露 PII | 模型准备输出完整手机号、地址或敏感 ID | 输出护栏脱敏/阻断；日志同样脱敏 | 展示完整数据、把原始 PII 传给模型 | 输出护栏和日志扫描测试 |
| ERR-12 | 实时事实缺失 | 商品价格或库存工具无结果 | 标明无法确认，建议稍后重试或人工 | 从商品说明 RAG 猜价格/库存 | 结构化事实来源测试 |

## 9. 数据、隐私与资金边界

### 9.1 Demo 数据声明

本项目全部演示数据必须为 synthetic 或 mock：

- 用户邮箱使用保留测试域名或明显的示例标识；不得使用真实个人邮箱。
- 订单号、物流单号、收件地址和电话号码为合成格式，展示时仍需按产品规则脱敏。
- 商品、SKU、价格、库存、订单、物流和政策由固定 seed 生成或由本项目创作的合成文件提供。
- 所有核心演示记录带 `is_synthetic=true` 或等价标识；前端和演示讲稿明确说明“合成演示数据”。
- Mock OMS 只能模拟状态，不连接真实商家、支付或承运商。

### 9.2 资金和权益边界

1. 本项目不接真实支付和真实退款，不产生真实资金流。
2. 退货工具只创建申请；审核通过也只是合成申请状态，不等于退款到账。
3. 任何退款、赔付、优惠券、免单、改价或金额修改只能由代码规则或人工操作产生结果。
4. LLM 只能读取结构化结果并解释；不得把自然语言中的“批准”转换为数据库或外部系统写操作。
5. 用户要求“立刻退款/赔偿/发券”时，系统可以解释规则或转人工，但不得承诺结果。

### 9.3 PII 最小化

- 不把完整手机号、地址、身份证、银行卡或收件人信息放进模型上下文、RAG 片段、工具响应摘要或普通日志。
- 必要字段按最小化原则返回，展示和审计使用脱敏值或哈希。
- 用户输入中的 PII 需要识别、限制传播和脱敏记录。
- 评测集、截图和演示视频不能暴露真实用户数据。

| 参考仓库的 recall、faithfulness、deflection、覆盖率和 benchmark | 其他仓库自报或小样本结果 | 不得作为 ShopMate 结果；只在来源调研中注明 |

没有 `docs/eval-report.md` 中的复现命令、配置、原始结果和版本信息时，任何百分比、提升倍数、节省金额或 ROI 都应标记为“未测量”，不得进入 README、演示字幕、简历或面试结论。

### 10.3 发布验证证据

每个 MVP 功能至少需要以下一种可复现证据：

- 单元测试或规则测试输出。
- API/集成测试输出。
- Playwright 端到端流程记录。
- 安全测试用例与通过结果。
- 评测原始 JSON/JSONL/CSV 和汇总报告。
- 容器健康检查、目标环境启动日志或可重复的 smoke test。

只有页面截图、口头演示或模型自述，不足以证明任务成功、权限有效或指标达成。

## 11. MVP 完成定义

阶段 2 的 PRD 完成不表示产品功能已实现。产品 MVP 只有在以下条件均满足时才可声明完成：

1. J1–J5 五条旅程可在 synthetic 数据上重复跑通。
2. F-01–F-25 均为 MVP 验收项。P0 用户故事对应的功能，以及权限、PII、资金、引用、幂等和高风险升级相关验收，必须全部有自动化或可复现证据；安全 P0 不得仅靠手工截图。P1 项允许在明确记录未完成范围并获得用户确认后延期，但不得放行上述安全关键项的缺陷。
3. 所有政策回答有可追溯引用；无证据和冲突政策有拒答/转人工。
4. 所有订单、物流、退货和工单访问均经过后端归属/角色校验。
5. 所有退款、赔付、优惠和改价边界均遵守第 9.2 节。
6. 退货申请和工单幂等测试通过。
7. 日志、模型上下文和演示材料不含完整 PII、密钥或系统 prompt。
8. 评测报告中的每个数字都能追溯到配置、数据集版本和原始输出。
9. Docker Compose 在用户确认的测试环境中健康启动，健康检查有实际输出证据。

## 12. 待阶段 3 固化的决策

以下事项不影响本阶段的产品边界，但必须在后续契约中明确：

1. 订单、库存和 Mock OMS 的统一错误码与 `as_of` 格式。
2. 退货规则配置、原因码、截止边界的数据库表达和审计字段。
3. `idempotency_key` 的作用域、生成方式、冲突返回和唯一约束。
4. 知识版本、地区、语言、有效期和引用对象的具体 schema。
5. 低置信度阈值、分类置信度阈值和评测基线。
6. SSE 事件字段、重连语义、取消行为和错误事件结构。
7. 客服与管理员角色是否使用同一入口、不同权限视图，以及店铺范围实现。
8. Milvus 固定版本、Embedding/LLM provider、fake provider 的替换边界。
9. 文件上传大小、格式、并发、解析超时和失败重试上限。
10. 日志保留期、审计保留期、PII 脱敏策略和评测数据保留范围。

在上述事项确定前，不得以猜测替代契约；任何会改变资金、权限或高风险行为的决策必须更新本文、相关契约和测试。
