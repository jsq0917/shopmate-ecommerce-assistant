### 1.5 证据门槛的标定

|---|---|

门槛取 0.62，位于 0.5836 与 0.6961 之间。首次评测使用 0.42 时 3 条无答案问题全部被
误判为“可回答”（`false_answer_cases=3`），据此把门槛上调并在同一数据集上复测得到的 1.00。
首次（未校准）的原始结果保留在 `data/eval/results/retrieval-20261019T033757Z.json`，
用于对比门槛变化前后的差异，不作为最终结论。
这是**在 17 条用例上标定的启发式阈值**，不是概率置信度；数据集扩大后必须重新标定，
边界偏窄（0.58 vs 0.70）意味着真实场景仍可能误收，因此保留“无引用即转人工”的二次护栏。

### 1.6 失败与限制

1. 语料小、文档短：21 个版本只切出 27 个子块（多数文档短于 480 字符的子块目标），
   检索的区分度天然受限。
2. 证据门槛依赖单一相似度信号，未使用 reranker 与跨编码器校准；`RERANKER_ENABLED=true`
   时会显式报 `RERANKER_NOT_CONFIGURED`，不会假装重排过。
3. 回答生成（LLM）未纳入本次评测：`LLM_*` 未配置时 `PolicyQAService` 直接抛出
   `ANSWER_MODEL_UNAVAILABLE`，不会退化成“只给片段但假装是答案”。
4. 冲突检测是确定性的“同一文档多个有效版本”，不覆盖跨文档语义冲突（例如两份不同文档
   给出不同的包邮门槛）；这类冲突需要阶段 8/13 的规则或人工标注支持。
5. 中文查询的 dense 相似度整体偏高（无关文档也有 0.3-0.5），阈值对语料变化敏感。

1. `exact_ref` 的 `false_refusal_cases=1`：`exact-05`（“2026.10.1 版退货政策替代了哪个

2. `near_dup` 的 `leak_cases=3`：这三条（near-01/03/05）金标文档都排第 1，但 4-8 个

   行为，但也说明 `forbidden_titles` 这一指标对“多文档取证”场景偏严，后续评测应区分
   “主引用错误”和“次要引用同主题”两种口径。

### 2.3 指标定义（避免"看起来很好"）

| 指标 | 定义（本次实现） | 备注 |
|---|---|---|
| Recall@k | 前 k 个**排序候选**中含金标文档标题的用例占比，分母 = 50 条有金标用例 | 文档级，非 chunk 级 |
| MRR@10 | 首个金标文档排名的倒数均值，只在前 10 名内计分 | |
| 引用准确率（主引用） | 第一条引用标题 ∈ 金标标题的比例，分母 = 期望"可回答"的用例 | 严格口径 |
| 引用精度（chunk 级） | 交付上下文中"标题属于金标"的 chunk 占比均值 | 4–8 片段必然稀释，故单独列出 |
| context precision | RAGAS 同构、金标代替 LLM 判定：交付片段中命中位置的 precision@k 均值 | 值域 0–1 |
| context recall | 交付上下文覆盖 `expected_phrases` 的比例均值 | 金标短语法 |
| faithfulness（结构化） | 答案逐句检查：句中每个数字必须能在工具卡片/引用载荷或用户原话中找到 | **确定性代理**，非 RAGAS |
| answer relevancy | BGE-M3 dense 余弦（问题 vs 答案） | **代理**，非 RAGAS 逆问题生成 |
| 任务成功率 | 行为符合预期 且 工具符合预期；安全类用例改判"无泄漏且无写副作用" | |
| 正确拒答率 | `expected_behavior=refused` 且实际返回固定拒答文案的比例（严格） | 另有 `no_fabrication_rate`：拒答或澄清即算 |
| 越权拦截率 | 带 `authorization` 标签的用例中"回答未包含他人订单号且无写操作"的比例，**分母写进原始结果**（`authorization_cases`），当前 **8** | 分母为 0 时返回 `null`，不再静默跳过 |
| 转人工召回/精确率 | 应升级用例被 `handoff_required` 的比例 / 预测升级中真正应该升级的比例 | |
| 延迟（聊天轮） | `ChatService.stream()` 整轮墙钟时间，`latency_kind=chat_turn`，**不含**政策检索轮与 handoff 决策短路 | 每条 record 落盘 `latency_ms` + `latency_kind` |
| 延迟（政策检索轮） | 仅 BGE-M3 编码 + 双路检索的墙钟时间，`latency_kind=policy_retrieval` | 与聊天轮分开汇总 |
| SSE 首 token | `first_delta_ms`，逐轮落盘到 records，可从原始结果独立复算 | 分母 = 有首 token 的聊天轮 |

#### 2.4.5 证据门槛标定（dev → test，防止"调到赢"）

只在 dev（29 条）上扫阈值，选择规则：行为正确率最高 → 误答最少 → 误拒最少 → 阈值更保守。

| 阈值 | dev 行为正确率 | dev 误答 | dev 误拒 |
|---|---|---|---|
| 0.50 / 0.55 / 0.58 | 0.9655 | 1 | 0 |
| **0.60 / 0.62** | **1.0000** | **0** | **0** |
| 0.65 | 0.9655 | 0 | 1 |
| 0.70 | 0.8276 | 0 | 5 |

dev 上 0.60 与 0.62 并列（都是 1.0000、0 误答、0 误拒），按"更保守"取 **0.62**，即现有默认值**不需要改**。

test（29 条）复测对照：

| 阈值 | test 行为正确率 | 误答 | 误拒 |
|---|---|---|---|
| 0.58 | 0.9655 | 1 | 0 |
| **0.60** | **1.0000** | 0 | 0 |
| **0.62（生产值）** | 0.9655 | 0 | 1 |
| 0.65 | 0.9310 | 0 | 2 |

即：如果允许看 test，0.60 会更漂亮（1.0000 vs 0.9655），差的就是 `exact-05` 那一条边界用例。
**但我们没有采用 0.60** —— 用 test 选阈值就是"调到赢"。这条差异如实写出来，
既说明 0.62 略偏保守（会牺牲极少数元信息类问题），也说明 dev/test 各 29 条的样本量下，
0.02 的阈值差异只对应 1 条用例，不足以支撑"更优阈值"的结论。

> 规模警告：dev/test 各 29 条，单条用例就能让比例跳动 3.4 个百分点。该标定只能作为"量级参考"，
> 不能当作统计显著的最优阈值。

### 2.9 失败案例分析

#### 2.9.0 唯一的 fail-open：`NO_EVIDENCE` / `CONFLICT` 哨兵可被引用标签绕过（P0，安全相关）

**触发条件**：回答模型把哨兵写在句首但后面跟了引用标签，例如 `NO_EVIDENCE [c1][c2]…`。

**代码路径**（`src/shopmate_ecommerce_assistant/rag/policy_qa.py`，`PolicyQAService.answer`）：

1. `if draft.strip() == "NO_EVIDENCE":` —— 精确相等，带标签时不成立 → 落到正常分支；
2. `commitment_issues(draft)` → 无命中；
3. `citation_issues(draft)` → `used_labels` 非空、标签都合法；逐句检查时该行含 `[cN]` → 通过；
4. `status="answered"`，答案原文返回给用户。

`CONFLICT` 走同一段逻辑，风险相同（本轮未复现，但代码结构一致）。

**实测影响**：36 条政策用例中 **2 条**（`eval-058`、`eval-061`）命中，
用户侧看到的是 `NO_EVIDENCE [c1][c2][c3][c4][c5][c6][c7][c8]`（见 `stage13-20261019T184441Z.json` 的 `records`）。

**为什么其他用例没触发**：`qwen2.5:7b` 在另外 20 条里输出了**纯** `NO_EVIDENCE`（无标签），
恰好命中了精确相等分支，于是被正确拒答。也就是说，这段逻辑的"正确"取决于模型是否画蛇添足，
**不是**由于校验本身严谨。

**建议修法**（需授权，属业务逻辑变更）：

```python
# 归一化后再判定：去 [cN] 标签、去空白、忽略大小写
normalised = re.sub(r"\[c\d+\]", "", draft).strip().upper()
if normalised == "NO_EVIDENCE":
    ...  # 走 refused
if normalised == "CONFLICT":
    ...  # 走 handoff
```

并补一条回归测试：`NO_EVIDENCE [c1]` 必须得到 `status="refused"`；`CONFLICT [c1][c2]` 必须得到 `handoff`。

**已修（阶段 16，2026-10-20）**：`rag/policy_qa.py` 新增 `sentinel_of()`——先剥离 `[cN]` 标签、
首尾空白与句末标点，再忽略大小写比对，命中即进入拒答/转人工分支；`citation_label_issues()` 也把
这一步放到标签校验之前（否则 `CONFLICT [c1][c2]` 会先报 `unknown_citation:c2` 而掩盖哨兵）。
回归覆盖见 `tests/unit/test_policy_sentinel.py`：`NO_EVIDENCE`、`NO_EVIDENCE [c1]`、`conflict。`、
`NO_EVIDENCE[c1].` 四类输入必须分别得到 refused / refused / handoff / refused，正常带标签答案不得误伤。

> **口径声明**：本章（含 §2.4.3、§2.9.1 的 #0、§2.9.4）的历史数字对应**修复前**的行为；
> `data/eval/results/stage13-*.json` 未改动、也未重跑全量评测。修复后的行为只由上述新增单元测试
> 覆盖，**不产生任何新的评测数字**。

### 2.11 局限与未运行项（务必与结论一起读）

1. **官方 RAGAS 包未运行**：政策答案是自建 prompt 的 LLM-as-judge（2.5.3），不是 `ragas` 实现。
2. **政策答案只覆盖 36 条、且只有 5 条真正生成成功**：可用样本极小，faithfulness 0.88 / relevancy 0.52
   的置信区间很宽；judge 与被测模型同族，存在**自偏好偏差**，绝对值不可外推。
3. **本地 7B 模型 ≠ 线上模型**：`qwen2.5:7b` 的过度保守（20/29 有证据仍拒答）不代表云端大模型的表现，
   也不代表本系统在强模型下的上限；反之亦然。
4. **成本只有本地口径**：政策答案部分记录 77,709 tokens、成本记 0 USD，因为推理在本机进行；
   **不能**据此得出"比云模型便宜 x%"——那需要同一批请求在云上跑一次的实测账单。
5. **语料过小**（27 条有效向量 / 20 篇文档），Recall@1 饱和到 1.00，**不能外推**到真实知识库；
   真实场景下 27→10⁴ 条量级时排序与门槛行为都需要重新标定。
6. **dev/test 各 29 条**，阈值标定只具量级参考意义，不构成统计显著结论。
7. **压测是单机单 worker、CPU 推理、提高限流的非常规配置**，不能当作生产容量承诺。
8. **数据集为合成数据**，问题由人工编写，可能存在与语料表述过度重合的偏差（这正是 Recall 饱和的原因之一）。
9. 压测只覆盖读路径；退货申请/转人工等写路径未纳入并发测试（避免制造垃圾工单）。
10. **数据集有重建字段**：eval-101…136 的 `reference_answer`、eval-107…110 的 `history`
    是本次按问句/期望行为补写的（原 136 条文件已丢失），见 2.2。期望值（question/intent/tool/
    behavior/risk/tags）全部来自 136 版 `records`，未被改动；但多轮路由结果受重建的历史影响（见 2.6 注）。
11. **结构化 faithfulness / relevancy 代理未落盘逐轮**：它们由（答案, 工具载荷）逐轮计算，
    载荷不持久化，因此只能重跑脚本复现；本轮已把 `latency_ms / latency_kind / first_delta_ms`
    逐条落盘，其余汇总（除这两个代理外）都可由 `scripts/verify_stage13.py` 独立复算。
