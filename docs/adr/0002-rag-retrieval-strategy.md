# ADR-0002：RAG 检索采用版本过滤、BGE-M3 双向量与 RRF

- 状态：已接受；2026-10-19 修订（稠密与稀疏固定为同一 BGE-M3 模型产出，取代原「sparse/BM25 可替换」方案）
- 日期：2026-10-18（初版）；2026-10-19（修订）
- 阶段：阶段 3；阶段 7 按修订版实现
- 相关文档：`docs/03-architecture.md`、`docs/04-data-contract.md`、`docs/07-security.md`

## 背景

ShopMate 的政策、保修、配送、FAQ 和商品说明具有版本、地区、语言、生效期和店铺范围。仅做 dense 检索容易：

- 召回语义相近但已过期或跨店铺的条款。
- 对订单号、SKU、政策编号等精确词不敏感。
- 在中文短查询或同义表达中排序不稳定。
- 让模型看到片段后自行拼出没有依据的条款。

课程给出了 dense + sparse/lexical 双路召回、RRF、重排和引用的思路。ShopMate 将其收敛为可审计、可测试的模块化单体实现，不使用不可见黑盒框架承载核心流程。

## 决策

知识检索采用以下固定管线：

```text
权限/店铺/地区/语言/有效期过滤
        |
        +-- dense(bge-m3, 1024) top 30 ---+
        |                                 |
        +-- sparse(bge-m3 lexical) top 30 -+--> RRF(k=60) -> 去重/版本聚合
                                              -> 可选 reranker
                                              -> 4-8 个片段
                                              -> 引用校验 -> 答案组合
```

1. **先过滤，后检索**：Milvus 查询带 `shop_id`、知识库、`locale`、`region`、`ready` 和有效时间条件。
2. **双向量同源**：dense 与 sparse 都由本地 BGE-M3（`BAAI/bge-m3`）在一次前向中产出。dense 为 1024 维、写入与查询两侧都做 L2 归一化，相似度用 `COSINE`；sparse 为 lexical weights 字典，写入 `SPARSE_FLOAT_VECTOR`，相似度用 `IP`。**不得用 BM25、jieba 词频或任何独立稀疏实现替代**，也不得在查询侧切换成别的 embedding 模型。测试使用 fake provider，不加载真实权重。
3. **RRF 融合**：按排名融合，不直接相加 cosine 与 sparse 的原始分数。两路各取 top 30，`k=60`，融合后保留最多 30 个候选。
4. **权威复核**：从 PostgreSQL 重新读取文档、版本、片段和权限元数据；过期、停用、未 ready、跨店铺或删除片段必须剔除。
5. **去重**：先按 chunk，再按父块/版本聚合；不同版本、地区和文档的同一文本仍保留独立元数据。
6. **可选重排**：默认关闭 reranker；启用时对最多 12 个候选重排，记录 provider、配置和耗时。
7. **上下文预算**：最终选择 4-8 个高价值片段，总 token 预算由配置控制；不把整篇文档塞入上下文。
8. **引用**：每个片段生成稳定 `citation_id`，携带 `document_id/version_id/chunk_id/title/heading/page/version/effective_from/effective_to`。答案只能引用本轮实际提供的片段。
9. **冲突/无证据**：若有效政策冲突、证据不足或无法确认适用范围，返回澄清/拒答/人工路径；不自行选择有利条款。

任一路向量或检索失败时，本次检索必须返回明确错误并记录审计，**不得静默降级为 dense-only 后继续回答**；降级结果不能计入双路检索的评测结论。

## 为什么固定 BGE-M3 单模型双输出

- 同一次前向同时产出 dense 与 sparse，两者共享同一 tokenizer 和语义空间，避免「稠密模型 + 独立分词器」之间的词表与权重口径不一致。
- 可完全离线运行，不依赖外部 embedding API，符合本项目的可复现要求。
- 稀疏权重与稠密向量由同一版本模型生成，模型升级时两路可一起重建，回归测试只需对齐一个版本号。

代价与限制：

- 权重约 2GB 级，CPU 推理延迟高于小型 embedding 模型；因此固定单 worker 加载或用独立服务承载。
- dense 固定 1024 维，与阶段 5 的 384 维哈希占位向量不兼容，阶段 7 必须重建 collection 并全量重导入。
- BGE-M3 的 dense 输出默认未归一化，必须显式归一化；漏做会导致相似度失真。
- 批量推理在个别环境下遇到 JSON/特殊符号可能产生 `NaN`，入库前必须校验并拒绝脏向量。

## 为什么用 RRF

RRF 只依赖排名：

```text
score(d) = sum over channels 1 / (k + rank_channel(d))
```

优点：

- 避免 cosine、BM25 分数量纲不同导致某一路压倒另一路。
- 对 provider/模型更换更稳定，便于回归测试。
- 排名过程可解释，可记录每路排名与最终融合排名。

RRF 分数不是概率，不能直接当作“政策正确置信度”。证据支持度必须由单独的规则、重排器归一化分数或人工审核定义；不得用 RRF 原始分数伪造置信度。

## 过滤与安全

- 用户和模型传入的 `shop_id`、权限不能改变过滤条件。
- 上传文件、HTML、Markdown 中的命令和链接作为普通不可信文本处理。
- 片段来源必须属于当前店铺知识库；引用片段被停用或版本过期后，不得继续返回旧答案。
- 缓存 key 至少包含规范化问题、shop、locale、region、知识库和知识版本；版本变化主动失效。
- 订单、价格、库存、物流、优惠不进入 RAG 事实路径。

## 备选方案

### 纯 dense

语义泛化好，但对精确编号/短中文不敏感，过期版本过滤压力更大。未作为唯一方案。

### 纯关键词/BM25

可解释、精确词好，但同义表达和自然语言问题召回差。未作为唯一方案。

### 稠密用外部 embedding API + 稀疏用 BM25

曾有方案让 dense 走 Qwen/OpenAI 兼容接口、sparse 走 BM25，以减少本地依赖。未采用，原因：

- 两路来自不同模型族，词表、分词口径和分数分布不可比，效果调优只能靠经验拼参数。
- 依赖外部网络与密钥，破坏离线可复现；CI 无法真实运行。
- 模型升级时两路要分别重建、分别回归，审计成本更高。
- 纯 BM25 对中文同义表达召回弱，双路互补性不如同源 M3。

### 直接用 Qwen3-Embedding 等更强 dense 模型

在 GPU 与精度优先场景下排序指标可能更高，但这类模型不输出稀疏权重，必须另配 BM25 才能做混合检索，退化为上一节的方案。本项目单机 CPU、无 GPU，且要求稠密稀疏同源，故不采用。

### 直接把 dense 和 sparse 分数相加

不同 provider 的分数不可直接比较，且模型升级会改变分布。未采用。

### 每轮自动多写子查询/HyDE

可能增加成本和不可解释性；MVP 允许最多 3 个受控子查询，HyDE 只作为可选实验，不能把伪回答当作事实。

### 用一整篇文档作为上下文

超出预算、放大注入面、降低引用精度。未采用。

## 后果

正面：

- 对语义问题和精确词查询都保留召回能力。
- 版本、店铺、地区、语言和时间过滤在检索前置与 PG 复核两层执行。
- 融合和引用对象可记录、可测试，便于后续 RAGAS/Recall@k 评估。
- provider 和 reranker 可替换，测试可以使用 fake fixture。

负面/风险：

- 需要维护两路索引和两路上游失败状态。
- BGE-M3 的 CPU 推理与模型加载需要额外内存（约 2GB 级），且 dense 固定 1024 维，索引体积比 384 维哈希方案高约 2.7 倍。
- 维度与模型版本变更必须重建 collection，不能就地升级；阶段 5 的哈希向量需要重导入。
- RRF 参数、最终片段数和上下文 token 预算需要基线评测；初始参数只是工程配置，不是质量结论。
- 版本冲突可能需要人工流程，不能完全自动化。

## 实施与验证

1. 阶段 5 生成版本化知识 fixture、父/子块、hash 和 fake embedding；该阶段的 384 维哈希向量只用于链路验证，不作为检索质量依据。
2. 阶段 7 实现 BGE-M3 provider（dense+sparse 同源）、1024 维 collection 重建与全量重导入、PostgreSQL 元数据复核、`hybrid_search` + RRF 和引用对象。
3. 测试过期版本、跨店铺、未 ready、停用片段、冲突版本和恶意文档；另测单路故障时必须报错而非降级。
4. 保存每次检索的过滤条件、双路 top-k、RRF rank、reranker 状态、`embedding_model`、耗时和最终片段。
5. 在独立评测集上测 Recall@k、MRR、引用准确率、无证据拒答率和上下文指标；必须包含 `dense-only` 消融对照，任何提升都要有 baseline、配置、数据集版本和原始输出。
